## 已实现的能力

| 能力 | MCP / 本机入口 | 权限和约束 |
| --- | --- | --- |
| 暂存、提交 | `git_write` 的 `add` / `commit` | 显式仓库与文件路径；本机仓库策略；预期 HEAD / branch；提交作者绑定；敏感路径与冲突检查。 |
| 推送、获取、同步 | `push` / `fetch` / `pull_ff_only` | 精确获批 HTTPS remote 和 branch；push 绑定计划 commit SHA；pull 要求干净工作树并只允许 fast-forward。 |
| 查看、创建、切换分支 | 只读 `git_branches`；受策略约束的 `branch_list` / `branch_create` / `switch` | 查看只需 `git.read`；创建与切换需写授权；切换不丢弃修改。 |
| 自定义 Windows 命令 | `level3_request` / `level3_request_status` / `level3_start` | 单独 `execution.level3` scope，默认关闭，本机审核完整请求与 digest，十分钟 TTL，单次授权。 |
| 生命周期与结果 | 原有 `execution_status` / `execution_job_output` / `execution_cancel` / `execution_list` | 分别要求 jobs.read / cancel scopes，OAuth client 隔离，输出字节预算，超时 / 取消 / 树清理结果。 |
| 本机权限管理 | `c2c git-write …` / `c2c level3 …` | MCP 不提供 enable、approve 或修改策略入口。 |

保留 V1.2 具名 recipe、Native Launcher / Helper、Node 和列出的包管理器启动材料完整性检查。
Native protocol v5 的原有 recipe 模式保持兼容，新增 generic payload；公共结果显式区分 `level3` 与 `git_write`。
V1.2 `DEFAULT_SCOPES` 保持原样。新 scopes 只加入 supported 集合，旧 token refresh 不会得到新能力。

没有开放 force push、hard reset、clean、删除分支、丢弃修改、高风险 rebase、任意 Git argv 或调用方自带远端 URL。

## 本机审核与 MCP 使用

以下使用开发 Worktree 的 CLI。仅应在明确选择的测试 workspace 中操作；本机 CLI 与 Bridge 必须使用同一 Windows 用户和同一有效 state root。
已有本机 permission mode 仍是独立门槛：`readonly` 拒绝启动，Level 1/2 本身不会授予 Git policy 或 Level 3 命令授权。

```powershell
$v13Cli = 'C:\codex\codex-with-chatgpt\worktrees\C2C-V1_3\bin\c2c.js'
$v13Workspace = 'C:\your\approved-workspace'
node $v13Cli --version
node $v13Cli permission status -w $v13Workspace --json
node $v13Cli level3 status -w $v13Workspace --json
```

Git policy 示例：保存为本机 JSON 后，先预览，检查真实仓库、作者、可执行材料、操作、分支与远端；再使用返回的完整 digest 批准。
`repository_path` / `--repository` 必须明确选择 workspace 内仓库根，例如 `WORK2`；根仓库使用 `.`。

```json
{
  "allowedOperations": ["add", "commit", "push", "fetch", "branch_create", "switch", "pull_ff_only"],
  "allowedBranches": ["codex/example-development"],
  "allowedRemotes": [{"name": "origin", "url": "https://github.com/example/project.git"}]
}
```

```powershell
node $v13Cli git-write approve -w $v13Workspace --repository WORK2 --policy 'C:\your\git-policy.json' --json
# 审核上一步预览后，将返回的 digest 填到下一条命令。
node $v13Cli git-write approve -w $v13Workspace --repository WORK2 --policy 'C:\your\git-policy.json' --approve --digest '<preview-digest>' --json
node $v13Cli git-write list -w $v13Workspace --json
```

需认证的远端可在 policy 中明确批准同一 Git for Windows bundle 内的 GCM exe；需代理时可明确批准规范 loopback HTTP proxy。
不继承宿主机 Git helper、全局 Git/proxy 环境或任意远端配置。具体配置约束见 [Git Write](v1.3-git-write.md)。

ChatGPT 先核对 `workspace_info`、本机权限、显式仓库的 `git_info` / `git_status` / `git_branches`，再发起 `git_write`。
每一步都传入真实 `expectedHead`、`expectedBranch` 和独立 idempotency key，并等待 job 结束、回读结果。
例如 add 结束后再检查 staged diff，commit 结束后获取新 HEAD，然后才对指定获批分支 push；不能复用提交前的旧 HEAD。
OAuth 授权须显式包含 `git.write`；结果查询与取消还需对应 execution scopes。升级或刷新旧 token 不会自动增加它们。

Level 3 必须先由本机操作员明确开启，然后 ChatGPT 才能创建 pending request。

```powershell
node $v13Cli level3 enable -w $v13Workspace --approve --json
node $v13Cli level3 list -w $v13Workspace --json
node $v13Cli level3 inspect -w $v13Workspace --request '<request-id>' --json
# 审核完整 exe、argv/command、cwd、timeout、材料和作用范围后批准。
node $v13Cli level3 approve -w $v13Workspace --request '<request-id>' --digest '<request-digest>' --risk development --approve --json
```

MCP `level3_request` 传入 `engine`（`program` / `powershell` / `cmd`）、绝对 `.exe` 路径、精确 args 或完整 command、workspace 相对 cwd、repository_path、timeout_seconds 和 materials。
PowerShell 7 固定 `-NoProfile -NonInteractive -Command`，CMD 固定 `/D /S /C`，program 不经 shell。
已知 Windows shell 不能伪装为 program 模式。启动还需同一 OAuth client、request_id、digest 和 idempotency_key。

破坏性或系统级命令的风险类别只能由本机审批人选择，须 `--risk destructive-system --allow-system --approve`。
这不是自动命令语义分类器；审批人必须检查完整命令。MCP 和模型无法自行作出本机审批。

```powershell
node $v13Cli level3 revoke -w $v13Workspace --request '<request-id>' --json
node $v13Cli level3 disable -w $v13Workspace --json
node $v13Cli git-write revoke -w $v13Workspace --repository WORK2 --json
```

权限变更由后续请求和 Supervisor poll 动态回读，无需为审批或撤销重启 Bridge。
使用新二进制与源码版本则需要单独的部署流程和运行时切换；本阶段未执行。

## 安全复核结论与边界

1. 身份、OAuth scope、本机授权、预期状态和执行材料由本机可信层检查。路径 escape、reparse、嵌套仓库与 Worktree 使用既有 repository identity 基础设施，并在 Native 创建进程前再次检查和锁定。
2. 禁用 hooks / filters / textconv / external diff；拒绝危险 Git 配置、URL rewrite、未知 helper、SSH、alternateRefsCommand、alternates 和 promisor / partial clone。TLS 验证开启；远端 URL 与分支精确匹配；push 绑定完整计划 HEAD SHA。
3. C2C 以 common Git directory 身份串行化同仓库和 Worktree 写入。未知或未确认清理的锁失败关闭，不按时间抢占。外部本机 Git 进程不遵守 C2C 锁；执行期间应避免其他客户端写入同仓库。
4. index 必须由 Git 更新，作为启动前摘要快照；switch 必须替换 HEAD，因此只对 HEAD 做启动前身份 / 摘要核对。其他操作会持有 HEAD 材料锁。这不是对全部外部 refs / index 变化的 OS 排他锁。
5. 失败、取消或中断后保存退出码和本地前后状态；网络结果可能是 `unknown`，且标记可能部分成功。`confirmationScope` 明确为 `local_repository`，不会声称远端未发生写入。
6. Level 3 以当前非提升用户运行，不调用 UAC。Job Object 控制进程树、超时与取消，但 cwd containment 不是 OS 文件系统、网络或恶意代码沙箱；被批准程序仍可访问当前用户在 cwd 之外的资源。
7. 绑定并锁定 exe 与明确列出的材料，不能冻结任意命令后续读取的所有文件。Windows、Git bundle 动态 DLL、GCM 外部运行时和用户批准程序的动态依赖仍属宿主信任范围；源码不额外认证安装 ACL 或发行者。
8. UTF-8 文本输出有上限和已知 pattern 脱敏；含 NUL 的 generic 输出受限，覆盖 UTF-16 / binary 常见情形。脱敏不保证发现任意编码秘密、跨 stdout/stderr 拼接或恶意程序外泄。禁止把凭据字面量放入审批命令。
9. 审计绑定 workspace、OAuth client、job、能力、request / digest、时间、状态、退出码和错误；服务重启不自动回放 interrupted job。
10. 每个 Bridge 进程最多同时执行两个任务，单仓库一个；同 state root 的跨 Bridge Git / Level 3 写入另有仓库锁。任务持久化最多 50 条，单任务 stdout / stderr 各 4 MiB，单次读取 64 KiB。Level 3 pending 最多 50、history 最多 256；Git 计划每 workspace 最多 256、每文件最多 1 MiB，原子创建锁限制并发，达到上限返回 `GIT_PLAN_STORE_FULL`。Git 计划不自动删除，需本机操作员审核后逐文件维护；未知遗留创建锁返回 busy，不自动抢占。
