# C2C Local V1.5 — Capability Delivery & Operational Observability

**状态：规划草案 / 尚未施工 / 待用户确认范围**

- 编写日期：2026-10-21
- 所属仓库：RomioLA/codex-with-chatgpt
- 规划依据：V1.4 功能分支 `feat/20261018-c2c-v14-native-workflow`；已部署 Runtime 基线 `a44ace150c865fc1aa3db94bdbcb9f72b0380a6e`。
- 文档所处阶段：V1.4 收尾与 V1.5 需求冻结前。**本文件不表示 V1.5 已实现、部署或被正式验收。**
- 优先事项：能力清单一致性、部署后的工具发现、权限/故障判别、AI 工具路由、有效使用率。
- 明确范围：当前以 Windows 本机 C2C + ChatGPT 连接为主，其他系统的能力差异须单独验证。

## 0. 三句话概述

1. V1.4 已在源码中实现通用执行、Batch 与持久 Task，但当前 ChatGPT 对话的 C2C 工具面仍缺少这些功能。**问题首先是“交付链路未被证实完整”，不是“再次设计执行器”。**
2. V1.4 先做一次**真实服务端 tools/list → ChatGPT 客户端工具发现 → 实际调用**的闭环验收。若只是客户端工具快照旧，不把这个问题包装为 V1.5 新功能。
3. V1.5 增加可重复运行的能力一致性门禁、来源清晰的故障诊断、部署/升级后的可操作提示，以及有意义的 C2C/Remote 选型统计，避免同类问题反复发生。

## 1. 背景、证据与不能得出的结论

### 1.1 本轮反馈

一次 Cinderella 独立审查报告中的**估计**：C2C Local 约 80 次调用、82%；Remote Desktop Commander 约 18 次调用、18%。Remote 主要用于 Production scoped-status、Vitest、TEMP 检查及异步进程输出查询。它是**单次审查样本**，按底层工具子调用而非耗时、Token、任务价值或历史所有任务计算。**不得把“82%”当作全局基线。**

该次报告还称当前 C2C 不暴露 `execution_run`、`batch_read`、`batch_search`、`collect_evidence`，因而不能执行原本应优先由 C2C 执行的操作。

### 1.2 当前可复核事实（以当时快照为准）

- 当前聊天可访问 C2C Local，`workspace_info`、`permission_status` 调用成功。Workspace ID 为 `9e005ae5cc15`；本机有效权限为 `level1`。
- 当前 ChatGPT 工具目录中可见 **39 个** `mcp__C2C_local__*` 工具，含 `execution_start`，**不含下面的 10 个目标工具**：
  `execution_run`；`batch_read`、`batch_search`、`collect_evidence`；`task_create`、`task_status`、`task_list`、`task_result`、`task_output`、`task_cancel`。
- 当前本机 Bridge 进程路径指向 V1.4 Runtime `versions/a44ace150c865fc1aa3db94bdbcb9f72b0380a6e`；这是进程身份线索，**不等于该用户的 ChatGPT 已刷新工具快照**。
- V1.4 对应 GitHub 源码：`src/mcp/server.ts` 注册 `execution_run`；`src/mcp/batch-tools.ts` 注册三个 Batch/Evidence 工具；`src/mcp/task-tools.ts` 注册六个 Task 工具；`src/mcp/oauth.ts` 装饰工具列表的 OAuth 元数据。
- 源码层面注册 ≠ 登录后该运行实例真实注册成功 ≠ MCP `tools/list` 返回 ≠ ChatGPT 已采集/启用 ≠ 当前对话实际可调用。
- 本次尚未取得**与当前客户端相同身份/授权上下文的原始线上 MCP tools/list 结果**，也尚未取得 ChatGPT 管理侧刷新后的新快照。因此**不能将“客户端缓存”宣布为已证实的单一根因**。

### 1.3 外部平台边界

OpenAI 关于自定义 MCP 应用的文档指出：对于其所覆盖的管理型应用/工作区，工具集合可能作为经审批的快照保存；管理员可在具备权限与连接的情况下刷新工具，新增操作可能默认未启用。**不同 ChatGPT 计划、应用创建入口、插件形态与 UI 并不必然有同一个 Refresh 按钮。**

参考（作为外部平台行为材料，不代替用户实际界面与 API 结果）：

- https://help.openai.com/en/articles/12584461-creating-custom-mcp-apps-in-chatgpt
- https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt

除非客户端/平台明确提供相应能力，C2C **不能**远程读取、修改、刷新 ChatGPT 内部的工具缓存或为用户代替 UI 审批。

## 2. 问题定义与成功标准

**问题定义：** 软件“已实现/已部署”与用户对话中“可发现/可授权/可执行”之间缺少可重复、可审计的交付一致性门禁，导致 AI 退回其他工具，并错误地解释为功能不足。

从使用者角度，成功必须逐层验证：

| 层次 | 问题 | 证据来源 | 判定 |
| --- | --- | --- | --- |
| L0 源码能力 | 对应工具是否实现、编译并在目标构建中注册？ | 指定 commit + 构建/test 证据 | 仅证明源码/构建 |
| L1 正式运行时 | 真实 Bridge 是否来自预期 Runtime，且版本/状态可信？ | 本机进程身份、Runtime 校验和部署记录 | 不单凭 PID |
| L2 服务端工具暴露 | 真实 `tools/list` 是否包含工具、schema、securitySchemes？ | MCP 协议真实响应（合适身份/范围），必要时区分授权状态 | 不以 grep 替代 |
| L3 ChatGPT 工具目录 | 当前连接器管理侧是否采集并启用了这些工具？ | 用户可见设置/受支持平台管理记录 | 本机不能自称已知 |
| L4 当前对话工具面 | 新对话实际获得哪些工具、参数是否正确？ | 在线验收会话的工具元数据 | 不以文档清单冒充 |
| L5 实际效果 | 只读、执行、Task 接口是否真实成功或按预期拒绝？ | 真实调用返回、Job/Task 结果 | 拒绝也需解释归因 |

**总体目标：** 能对每次缺工具/拒绝给出来源明确、可复核的结论；对于已具备、已暴露、已授权且无 GUI/UAC 限制的操作，优先使用 C2C，不因旧说明和错误调度而退回 Remote。

**非目标：** 不以增加工具数量、机械达成 95% 调用份额、自动提权、绕过 ChatGPT 插件权限，或让 Task 自主规划作为 V1.5 成功标准。

## 3. 根因假设与排除顺序

在有证据前，保留多个竞争假设：

| ID | 假设 | 若为真预计看到什么 | 如何证伪/区分 |
| --- | --- | --- | --- |
| H1 | ChatGPT 保存的连接器工具快照旧 | L2 有 10 个新工具，L3/L4 没有；受支持的刷新/审批后出现 | 比对同版本同连接端点的 L2/L3/L4 |
| H2 | 管理侧新操作未启用 | L3 能扫描新操作但不可选或禁用 | 检查管理 UI 的操作配置/权限 |
| H3 | MCP tools/list 注册、schema 或 OAuth decoration 兼容性故障 | L2 缺工具、列表返回错误或 schema 被过滤 | 使用真正 MCP client 在同一 Runtime、同一身份类型下读取原始列表 |
| H4 | 实际连到了别的 Connector / Workspace / Runtime | L1/L2/L4 的 URL、workspaceId 或构建身份不一致 | 同时检查工作区/endpoint/Runtime 身份；不得只看显示名称 |
| H5 | OAuth token 缺少 scope | 工具可见但调用返回 `INSUFFICIENT_SCOPE`，或特定客户端只暴露部分操作 | 单独核对 scope、工具授权模型与真实请求；不把 Level1 当 scope |
| H6 | 本机 Level1，缺少 Level2 Full Access grant | `execution_run` 的调用被本机拒绝，但只读 Batch 应仍可执行（若有 scope） | 对已暴露工具进行只读测试，按用户授权单独做 Level2 执行测试 |
| H7 | 当前对话/工具展示策略限制 | 管理侧已有工具，但某个聊天未选中应用或策略不提供调用面 | 同一账号新对话明确选择应用；查该会话工具面 |

排查顺序：**先验证工具是否存在及运行身份（L1/L2），再看平台工具快照（L3/L4），最后区分调用权限（L5）**。不得由于 Level1 就推断 L2/L4 工具必然应当被隐藏。

## 4. 版本范围与架构约束

### 4.1 沿用 V1.4 已有功能

- `execution_run`：通用 `program/powershell/cmd`，`cwd` 不是安全沙箱；要求当前 Level2 Full Access + 相应 OAuth scope，不能偷换为旧 `execution_start` recipe 流程。
- Batch：`batch_read` 最多 16 个文件、`batch_search` 最多 8 个查询；`collect_evidence` 按所请求分区校验 scope；结果与扫描预算均须有界。
- Task：六个 `task_*`，用于有限、确定性、不可变计划；不自行调用模型或增添步骤。`WAITING_FOR_MODEL`、副作用结果不确定、不自动 replay 等 V1.4 保护不变。
- Host Observation、受控 Git Write、token/OAuth、登录自启及原生 Helper/Launcher 完整性合同沿用现状。

### 4.2 V1.5 不改变的安全边界

1. 不新增无人审批的权限提升、无限制删除、任意敏感目录读取或 OAuth scope 绕过。
2. 不将 Host Observation `system.read` 变成泛用 shell。
3. 不把 Runtime 自检结果当作 ChatGPT 客户端状态的权威来源。
4. 不以刷新工具名义删除现有 OAuth、重置 workspace ID、改动 Named Tunnel、覆盖 Production state、重建 ChatGPT 连接器。
5. 不把 Job Object 误描述为 OS 文件系统/网络沙箱。
6. 不为提高“C2C 占比”而禁止确有必要的 Remote（例如 C2C 自身完全不可用、Windows GUI/UAC、当前协议缺能力）。
7. 本项目技术文档和工具描述只用于建议；本机权限、OAuth、用户当次请求及真实工具 schema 仍为最终约束。

## 5. V1.5 功能规格（提议）

### F1 — Capability Inventory / 分层能力清单（P0）

**目标：** 对 L0/L1/L2 形成可机读的本地/服务端证据；对 L3/L4 明确展示未知而不是虚构状态。

建议增加本机只读 CLI 子命令（最终名称在实施阶段以 CLI 设计评审为准）：

`c2c capabilities status -w <workspace> --json`

建议输出合同：

~~~json
{
  "schemaVersion": 1,
  "workspaceId": "example-id",
  "runtime": {
    "version": "example",
    "buildId": "example",
    "identityVerified": true
  },
  "toolInventory": {
    "source": "live_mcp_tools_list",
    "observedAt": "ISO-8601",
    "observedToolCount": 0,
    "requiredToolGroups": {
      "genericExecution": ["execution_run"],
      "batchEvidence": ["batch_read", "batch_search", "collect_evidence"],
      "persistentTask": ["task_create", "task_status", "task_list", "task_result", "task_output", "task_cancel"]
    },
    "missingRequiredTools": [],
    "schemaValidation": "PASS"
  },
  "client": {
    "chatgptCatalogVisible": "UNKNOWN",
    "chatgptConversationVisible": "UNKNOWN",
    "clientRefreshStatus": "NOT_OBSERVABLE"
  },
  "capabilityGate": "SERVER_PASS_CLIENT_UNVERIFIED"
}
~~~

此 JSON 是**拟议 schema 示例**，不是现有命令或当前真实输出；`observedToolCount=0` 是占位数据。实现时务必提供 `source` / `observedAt` / `errorCode`，并区分：

- `EXPECTED_FROM_BUILD`：编译产物声明的能力；
- `REGISTERED_IN_PROCESS`：运行时工具注册完成；
- `LIVE_MCP_LIST`：真实协议 `tools/list` 响应；
- `CHATGPT_CATALOG`、`CHATGPT_CONVERSATION`：只有外部验收输入，不能由本地猜测。

**重要设计决策：** 不要为了“诊断简单”把 OAuth token、HTTP auth header、管理员令牌、配对码、云端凭据或可执行命令明文写入 report/log。需要 MCP 授权时在受控的本机测试会话中完成，返回最小的工具名/安全元数据摘要；无授权则明确返回 `UNVERIFIED_AUTH_CONTEXT`，不是伪造成功。

总工具数应通过实际查询计算；不得把“当前 ChatGPT 39 + 理论新增 10 = 49”硬编码为所有部署的正确工具总数。以**具名集合比对 + schema 检查**为核心。

### F2 — Delivery Parity Gate / 发布一致性门禁（P0）

每次部署和连接器升级应产生以下分层状态：

- `BUILD_REGISTERED=PASS|FAIL|UNKNOWN`
- `RUNTIME_IDENTITY=PASS|FAIL|UNKNOWN`
- `MCP_LIST_LIVE=PASS|FAIL|UNKNOWN`
- `OAUTH_METADATA=PASS|FAIL|UNKNOWN`
- `CLIENT_CATALOG=PASS|FAIL|UNVERIFIED`
- `CHATGPT_LIVE_CALL=PASS|FAIL|UNVERIFIED`
- `FINAL_DELIVERY_GATE=PASS|BLOCK|PENDING`

**判定约束：** 只有 L2 工具已验证 + L3/L4 确实可见 + L5 最小真实调用成功，才允许将“正式 ChatGPT 全能力交付”标记为 PASS；L3/L4 无法观测时必须 PENDING。`BLOCK` 用于真实失败，不能把“未做外部验证”硬判 FAIL。

不得因新工具暂时未刷到客户端而打断正在正常运行的旧功能；诊断门禁失败不自动重启健康 Bridge/Tunnel，也不撤销 OAuth。

### F3 — Refresh / Update Runbook / 人机协作刷新指引（P1）

产品提供清晰的**检测—提示—验收**指引，而非假设能自动操作 ChatGPT：

1. 先确认现有连接器的 workspaceId、MCP Endpoint、OAuth 连通性、正式 Runtime；保存非敏感状态。
2. 读取 live tools/list，并把缺失差异归为“服务端缺失 / 客户端未启用 / 当前对话不可见 / 授权拒绝 / 未验证”。
3. 如果平台当前账户与 UI 支持对已存在的自定义 MCP 应用**刷新工具 / 配置操作**，提示用户在该应用管理界面操作；不替用户伪造按钮或权限。更新前后比对新旧工具清单。
4. 如果平台没有刷新入口，应说明能力边界，收集截图和应用创建方式；**不能默认要求删除连接器或重新配对**。重建连接仅作为明确了解影响、保存回滚信息后的最后手段，由用户单独同意。
5. 用户刷新后，**新对话**明确选择相同 C2C 应用/连接器，重新检查工具列表并做实际调用；报告 L2/L3/L4/L5 状态。
6. 如果新工具出现但调用报 `INSUFFICIENT_SCOPE` / `LOCAL_PERMISSION_DENIED`，转入权限诊断；不要以重新刷新代替授权修复。

支持文档的 UI 入口因版本/计划可能变化；对没有权限管理应用的普通用户，应使用条件指引或请管理员处理。不得把 Enterprise/Business 管理界面的“Refresh”断言成所有个人用户都存在的按钮。

### F4 — Reason-coded Fallback / AI 选型与降级归因（P1）

新增（或强化）一份明确工具路由规则：

- 源码/Git/文件/主机观察：按 C2C 有界专用工具优先。
- 多文件与多搜索：存在并可用时优先 Batch，但小范围单一查询不强制批量化。
- 通用命令：`execution_run` 已暴露且符合 Level2/OAuth/用户任务授权时优先；不要先走 `execution_start` 然后把 `COMMAND_NOT_APPROVED` 当成通用执行失败。
- 固定可恢复多步任务：适合的情况使用 Task，但单条命令不强迫包装 Task。
- Remote 只用于 `C2C_OFFLINE`、`CAPABILITY_UNAVAILABLE`、`GUI_UAC_REQUIRED`、`USER_EXPLICIT_REMOTE` 或其他能说明的正当原因；仅当用户授权及工具自身权限允许时操作。
- 若 C2C 能力已暴露但返回安全/授权拒绝，不得自动换 Remote 绕过。`OAUTH_SCOPE_DENIED`、`LOCAL_GRANT_MISSING`、`POLICY_DENIED`、`USER_NOT_AUTHORIZED` 应当停止，报告正确下一步。

错误原因应保留 `toolName`、`operationClass`、`stage` 与受控的 `reasonCode`；不为统计目的复制敏感命令、文件内容或 token。

### F5 — Tool-use Metrics / 有效使用率统计（P2）

**不把 95% 绝对比例作为门禁。** 设计用于调查“本可由 C2C 完成，却不必要地调用 Remote”的有效指标：

- `eligible_operations`：C2C 已暴露、授权且具备技术能力的操作总数；
- `c2c_handled_eligible`：其中实际由 C2C 完成的操作数；
- `avoidable_remote`：有证据证明当时 C2C 能满足需求、却选择 Remote 的操作数；
- `necessary_remote`：GUI/UAC、C2C 自修复、缺能力等有正当理由的 Remote 操作数；
- `fallback_reason_known_rate`：可解释 Remote 调用比例；
- `capability_gate_pass_rate`：发布后新会话中 L2–L5 门禁通过的比例；
- `round_trips_per_review`：典型审查的工具往返次数，仅作辅助。

主指标建议为 `avoidable_remote / eligible_operations`（目标尽可能接近 0），并记录排除规则。报告“C2C 占 95%”可以是看板参考项，但**不同任务类型与轮询策略会显著扭曲此比率**。

初期采用**一次性离线样本复盘或显式启用的聚合计数**；不引入默认上传、长期记录用户命令、默认外部遥测或跨 workspace 混合统计。

### F6 — Review Session Efficiency / 审查流优化（P2）

基于真实 Cinderella 工作流，选取下列样本进行演练：

- 开始：验证 workspace、目标嵌套 repo/worktree、分支与未提交状态；
- 代码：先有界 Batch 搜索，再按 source hash 读文件/收集证据；
- 测试：单次 `execution_run` 启动 Node/Vitest；返回 job 后用 status/output 分页，而非每次轮询都启动新进程；
- 完成：统一记录测试结果、产物与权限/原生环境状态；
- 不在“只读审查”中偷偷写源码、修改 Production、清理临时文件或启动破坏性测试。

支持进程输出流时继续复用现有 JobStore 分页与大小预算，不为“方便看输出”增加无界 stdout 或绕过脱敏。

## 6. 施工阶段与交付物（建议）

### Wave 0 — V1.4 收尾与真实问题归因（**V1.5 开工前**）

**不改源码、不变更 Runtime 为默认策略。** 取得以下四份独立证据：

1. 真实正式 Runtime 身份 + workspaceId + 现有 `status` / `autostart status`；
2. 同 Runtime 的 MCP `tools/list` 原始工具名/必要 schema/security 元数据，保留**如何认证、什么客户端、何时取得**；
3. ChatGPT 现有应用/连接器管理侧能看到的工具清单、刷新/操作启用结果（因计划不同可注明“不适用/未提供”）；
4. 新对话对 `workspace_info`、`batch_read`、`execution_run`、`task_status` 等**实际可见性与最小测试**。

**Wave 0 未完成就保持 `V14_CHATGPT_TOOL_PARITY=PENDING`。** 不因为 GitHub 新增文档、当前 level1 或 Bridge PID 正常而写 PASS。

### Wave 1 — Capability Contract & CLI Diagnostics（P0）

- 冻结 L0–L5 数据模型、来源和 error code；明确哪个结果本地可以观察、哪个只能外部提供。
- 实现不泄漏机密的工具清单来源检测与差异报告（CLI 名称待评审），并为 read-only / no-auth / auth-scoped 测试分别设边界。
- 按具名工具集合及 schema 检查，而非固定个数；增加 schema drift、注册失败、旧客户端快照等夹具。
- 不改 execution/Task 的已有权限逻辑与生命周期。

交付：规格合同、只读诊断实现、单元/集成测试与脱敏报告样本。

### Wave 2 — 连接器更新指导与外部验收（P1）

- 在安装/升级文档中明确“服务器已部署不等于 ChatGPT 已刷新”。
- 制作按用户界面能力分支的更新指引；新工具可能需单独启用。
- 提供在线 Acceptance 模板（先列工具，后实际调用）和缺失原因归因格式。
- 不写能够擅自修改 ChatGPT 账号设置的自动化，不要求用户无条件重新配对。

交付：升级 Runbook、可复用验收脚本/人工表、故障分流文档。

### Wave 3 — 工作流效率与统计（P2）

- 在有界样本上比较传统单次读取/轮询与 Batch/Task 合适使用时的调用量；
- 记录因 C2C 缺失导致的 Remote 与非必要 Remote，区分运行时间、调用次数和 token；
- 只在收益经过样本证明后决定是否实现新的聚合统计功能。

交付：真实审查样本、指标计算说明、优化前后对照与成本分析。

### Wave 4 — 发布门禁与文档同步

- 只对改变的模块跑定向回归、构建、typecheck、diff check；原生 Helper / OAuth / Lifecycle 边界变更才扩大相应安全门禁。
- Windows 实机验证 CLI/Bridge/Tunnel 不退化，现有 OAuth/Named endpoint 不丢失；
- 新用户/新 AI 教程与 `skills/c2c-local/SKILL.md` 更新，保证引用已存在的真实 CLI 工具；
- 明确发布版本、目标分支、安装路径与如何刷新连接器；合并 main/发布 Release 仍是单独发布决策。

## 7. 验收用例矩阵（至少包含）

| ID | 用例 | 预期 |
| --- | --- | --- |
| T01 | 源码已注册，但正式 Runtime 尚未升级 | 报 `RUNTIME_MISMATCH`，不说工具已可用 |
| T02 | Runtime 新、L2 tools/list 含目标、ChatGPT 工具目录旧 | 报 `CLIENT_CATALOG_STALE_SUSPECTED`，待平台侧比对 |
| T03 | L2 tools/list 缺 `execution_run` | `SERVER_EXPOSURE_FAIL`，不能叫用户盲目重新配对 |
| T04 | OAuth scope 不足 | `INSUFFICIENT_SCOPE`，不得误报成工具不存在 |
| T05 | Level1 下实际调用 Full Access | 按本机授权拒绝；只读 Batch 可单独验证 |
| T06 | 用户没有 Refresh 权限/界面入口 | `CLIENT_REFRESH_UNAVAILABLE`，保留连接，说明有条件的下一步 |
| T07 | 刷新后新增操作默认关闭 | 提示管理侧启用与风险审核，不自动允许写入 |
| T08 | 新对话工具可见、调用 success | 标记 L4/L5 PASS 并保存最小证据 |
| T09 | 新对话工具可见、调用失败 | 保留“可见=PASS、执行=FAIL”的两层状态 |
| T10 | Token/authorization 更换，旧 grant 不含新 scopes | 不自动扩权，按授权流程明确处理 |
| T11 | Task 异常恢复时 child 结果不确定 | WAITING_FOR_MODEL / 未知副作用不重放 |
| T12 | C2C 完全掉线需独立 Remote 恢复 | Remote 有正当原因，不视为调度退化 |
| T13 | 可由 C2C 执行却走 Remote | 记录 `AVOIDABLE_REMOTE`，以实际权限和工具面为判定依据 |
| T14 | 诊断采集时缺少外部客户端证据 | `CLIENT_UNVERIFIED`，最终 PENDING，不编造工具数 |
| T15 | Native Build/TaskStore/敏感路径异常 | 维持原有 fail-closed，不因可观测性功能扩大访问 |
| T16 | 工作区嵌套 Git/worktree 目标不一致 | 停止操作并报告实际 identity，避免误审/误写 |
| T17 | 公开自检降级（Named ECONNRESET）但工具调用成功 | 仅 diagnostic degraded，不重启健康 tunnel |
| T18 | 日志内容含令牌/机密/命令 | 报告应脱敏且有上限，不向第三方自动发送 |
| T19 | 同一 ChatGPT 应用在旧/新对话行为不同 | 记录会话/平台差异，不用“本地已运行”替代 L4 |
| T20 | 自动登录恢复后工具快照仍旧 | 明确 OS 自启成功与客户端工具更新是两件独立事 |

测试中可以使用本地隔离的命令与工作区；不得为了验证“能力已部署”而在正式用户数据上做破坏性实验。

## 8. 外部在线验收协议（草案）

**阶段 A：观察，不执行通用命令**

- 在 ChatGPT 新对话明确选择现有 C2C 插件，要求列出此会话实际可用的工具名；
- 调用 `workspace_info` 和 `permission_status`，比对 workspaceId、本机权限；
- 若可见 `batch_read`，读取指定普通测试文件，确认输出分页和错误处理；
- 若可见 `task_status`，在有合法测试 task ID 的情况下查询；没有 ID 时只报告工具是否存在，**不自动创建持久 Task**。

**阶段 B：通用执行，需另行明确授权 Level2**

本机操作者在授权后设置本次 Windows 登录会话的 Level2；实际 ChatGPT OAuth scope 也须允许 `execution.run`。在**隔离测试目录**执行：

~~~text
engine=program
executable=node
args=["-e","console.log('C2C_V15_TOOL_GATE_OK')"]
cwd=<isolated test directory>
timeout_seconds=30
idempotency_key=<new unique 16-128 character key>
wait_seconds=10
~~~

上述是参数示意，不是给用户盲复制的实际 MCP 请求。成功证据为：启动/完成结果、exit code=0、stdout 含特定标记、Job 身份来自 C2C，且**未使用 Level3 或 Remote 代跑**。完成后权限如需回退，由用户在本机按其授权决定。

**阶段 C：报告**

~~~text
C2C_RUNTIME_IDENTITY=PASS|FAIL|UNKNOWN
V14_SERVER_TOOLS_LIST=PASS|FAIL|UNVERIFIED
V14_CHATGPT_CATALOG=PASS|FAIL|UNVERIFIED
V14_CHATGPT_CONVERSATION_TOOLS=PASS|FAIL|UNVERIFIED
BATCH_READ_REAL_CALL=PASS|FAIL|NOT_RUN
EXECUTION_RUN_REAL_CALL=PASS|FAIL|NOT_AUTHORIZED|NOT_RUN
TASK_API_VISIBILITY=PASS|FAIL|UNVERIFIED
OAUTH_REPAIR_PERFORMED=YES|NO
EXISTING_CONNECTOR_PRESERVED=YES|NO
V14_DELIVERY_CLOSURE=PASS|BLOCK|PENDING
~~~

如果没有明确客户端能力证据，`V14_DELIVERY_CLOSURE` 不能报 PASS。

## 9. 工程工作分配、依赖与风险

- **工作 A / Protocol & OAuth**：Live tools/list、schema/securitySchemes 一致性、不同 scope 的客户端行为，禁止触及真实 token 明文。
- **工作 B / Runtime & CLI**：已部署 Runtime 身份、只读诊断报告、不可观测信息的 UNKNOWN 表达、Windows 自启后版本证明。
- **工作 C / ChatGPT Acceptance**：管理界面的操作更新流程、是否有刷新能力、会话工具列表与真实调用；这需要真实 ChatGPT 侧配合，本地子代理不能凭猜测代替。
- **工作 D / Skill & Docs**：更新当前 AI 路由/恢复手册，版本化使用说明，避免旧路径、旧截图与过时的 Level3 描述。
- **总控**：冻结字段/API 合同、合并验证、把离线通过和线上交付分别写入门禁；防止多个代理碰正式 state。

依赖顺序：Wave 0 首先区分客户端/服务端；Wave 1 明确诊断对象和数据源；Wave 2 基于真实平台入口；Wave 3 必须建立真实基线；Wave 4 最终发布。可以并行做只读调查与文档，但**对外工具接口合同、OAuth metadata 与 Runtime release 不应由多方独立修改后直接推送**。

主要风险：客户端权限差异导致误判；权限测试变成高权限执行；诊断泄漏凭据；维护者机器上旧源码 checkout 与新 Runtime 混用；外部平台工具列表限额/行为变化；重新配对破坏稳定的 Named endpoint；把审查中单次 18% Remote 比例过度解释。

## 10. 冻结前必须回答的问题

1. 用实际认证身份读取 L2 tools/list 后，10 个目标工具是否全部存在且 schema 正确？
2. 当前连接器属于哪个 ChatGPT 应用/插件创建入口？是否实际支持刷新/更新/启用工具？
3. 刷新后仍缺失的工具是否与 OAuth securitySchemes、SDK tools/list 结构或客户端限制有关？
4. 对于纯只读 Batch，level1 权限下是否可见且可调用？如果不行，服务器还是客户端拒绝？
5. 安全运行一次 Level2 `execution_run` 后，Job 跟踪、权限与 output 是否正确？
6. V1.5 的只读 CLI 诊断接口是否真有必要？现有 status/doctor 能否扩展而不混淆语义？
7. 是否需要支持其他聊天客户端？若要支持，应明确不同客户端的工具快照与认证特性，不能直接复用 ChatGPT 管理按钮描述。
8. 是否已经有代表性审查样本与计数方法支持 Wave 3 的实际收益？

## 11. 版本交付与记录原则

- 本计划作为 `docs/v1.5-plan.md` 保留**完整决策背景**，不要随着后续实现把历史调查、误判风险、设计选择和未验证事项压缩到几行。
- 任何确认结论应附日期、运行时 commit、实际 tool source（Build / Live tools/list / ChatGPT 实际调用）以及数据采集边界。
- 已完成的 Wave 保留 `设计 → 实施差异 → 测试 → 实机验收 → 剩余风险` 小节；架构变化通过修订记录追加。
- 开始施工前用户确认 V1.5 范围及分支策略；本文件提交不构成用户授权执行部署、更改插件设置、提升权限或触碰 Production 数据。
