## 2. 对抗式审查后的核心裁决

### 2.1 不建立新的全局 Capability Truth 系统

Draft 0.3 曾建议新增 `src/capabilities/*`，统一聚合 Runtime、MCP、OAuth、permission、Git policy、ChatGPT catalog 等状态。

Draft 0.4 取消这一默认方案。

原因：

- V1.4 已经有多个真实 enforcement point：
  - `src/process/recovery.ts`
  - `src/process/daemon.ts`
  - `src/bridge/instance-lock.ts`
  - `src/bridge/runtime.ts`
  - `src/permission/store.ts`
  - `src/git-write/registry.ts`
  - `src/git-write/planner.ts`
- 再建立一个中央“能力真值”模块，容易形成第二套判断逻辑；
- 同一 Runtime 对不同 OAuth client、workspace、repository 和具体 operation 的有效权限本来就可能不同；
- 诊断可以聚合证据，但不能成为新的授权者或新的真值源。

**Draft 0.4 原则：权威判断留在原 enforcement point；只补充必要的错误原因、只读状态和修复指引。**

### 2.2 Full Access 与 Git Write 的授权关系是 V1.5 的第一优先级

当前存在两条 Git 写入路径：

1. Level2 Full Access 下，通过 `execution_run` 运行普通 Git 命令；
2. 结构化 `git_write` 工具，额外受 repository policy 约束。

这两条路径的产品语义尚未完全统一。

如果 Full Access 已经允许正常 Git 命令，而结构化 `git_write` 对同一合法操作增加大量额外审批，就会出现：

> 更结构化、更安全的工具，反而比普通 shell 更难使用。

V1.5 首先要明确：

- Full Access 下，正常 Git 工作应具有什么默认能力；
- 结构化 `git_write` 的额外价值是什么：
  - expected HEAD / branch 防陈旧写入；
  - 结果验证；
  - 结构化操作；
  - 可审计结果；
- 哪些 repository policy 是 Restricted/Level1 的必要安全边界；
- Full Access 下是否还需要相同粒度的 repository approval；
- worktree 是否可以在证明 Git common repository identity 后复用 approval。

**不得在没有产品决策之前简单删除现有 Git policy，也不得为了维持旧 policy 再建设一套大型 Git Diagnose 平台。**

### 2.3 先把恢复“做得好用”，再考虑无人值守 Watchdog

2026-10-25 实际发生多次 C2C 中断，已通过正式 `restore` 恢复正常工具调用，但反复停止的触发源尚未定位。这将**最小故障取证**提前为 Stage 1 前的 P0.5；它不是恢复成功率已验证的证据，也不自动授权安装 Watchdog。

V1.4 已有：

- `status`
- `restore`
- `doctor`
- Bridge/runtime identity 检查
- instance lock
- daemon/recovery
- Launcher

旧 `.verification-c2c-watchdog-pairing-launcher` worktree 进一步实现了较复杂的：

- runtime identity；
- bridge ownership；
- watchdog；
- singleton；
- recovery lease；
- recovery policy；
- failure snapshot；
- active runtime；
- Windows owner verification。

这些实现可以作为技术参考，但 Draft 0.4 **不默认移植**。

原因：

- 自动恢复机制越复杂，越可能因为保守条件过多而真正故障时不敢恢复；
- 也可能误伤运行中的长任务；
- 可能形成新的 runtime authority / ownership truth；
- 常驻监控自身也会成为新的故障源；
- 当前尚无足够真实故障频率和收益数据证明整套 watchdog 值得进入 V1.5。

V1.5 优先解决：

- Bridge 已停止时，现有恢复入口能可靠恢复；
- Bridge 状态不明确时，明确告诉用户为什么不能安全重启；
- 启动器只使用正式 Runtime，不回退过时工作区；
- 活动 Job/Task 不被静默重放；
- 恢复后能重新查询合法 Job/Task 状态；
- 连续故障不形成无限重启。

后台常驻 watchdog、自动杀进程、recovery lease、多层恢复策略延后，除非施工期间发现真实问题证明必须引入。

### 2.4 Metrics 不作为 V1.5 产品功能

Draft 0.3 的 `avoidable_remote`、`eligible_operations` 等指标可以用于一次性离线复盘，但不再开发正式 Metrics 系统。

原因：

- C2C 本地无法可靠看到 ChatGPT 全部调度过程；
- 当前缺少足够长期样本；
- 为统计再引入状态、日志、持久化或遥测不划算。

允许：

- 在 V1.5 最终验收中人工/离线统计一次；
- 用于判断 Skill/路由是否明显改善。

不允许：

- 为 V1.5 新增长期默认遥测；
- 建立独立 Metrics 服务或数据库；
- 把“C2C 使用率必须达到某个百分比”作为发布门禁。

### 2.5 Release Gate 缩减为三类真实验收

不建立新的持久 Release Gate 状态机。

只保留三类：

1. **本地功能回归**
   - 定向测试；
   - typecheck/build；
   - Level1/Level2/OAuth/Git 安全边界不退化。

2. **Windows Runtime 验收**
   - 正式 Runtime/Bridge；
   - execution；
   - Job/Task；
   - 状态/恢复。

3. **ChatGPT 在线验收**
   - 本版本承诺的工具真实可见；
   - 最小真实调用成功；
   - 失败能正确归因。

平台侧暂时无法取得某些 catalog 信息时，可以标记客户端证据未验证，但不能因此把已经正常工作的本地 Runtime 判成失败。

### P0.5 — Bridge 连续中断的最小退出与无响应归因（Stage 1 前）

**现场原因：2026-10-25 多次 C2C `internal tool error` / Bridge 失联，经正式 `restore` 后实际工具调用恢复；重复停止的触发源尚未定位。**

严格区分两类故障，不能将它们当成同一个根因：

- **进程已消失**：历史上既有 `Bridge stopped` 的停止，也有 PID 失效但无关闭日志的停止。前者可能来自 CLI stop/restart、默认自动修复的 `doctor`、Tunnel 选择/修复等正常代码路径，但目前不知道是谁触发；后者缺日志并不能直接证明被杀、崩溃或系统重启。
- **进程存活但无响应**：若本机 `/health` / MCP 也超时，要考虑 Event Loop 阻塞；同步 Git、Execution Job 输出/状态同步 I/O、同步 logger/权限轮询是候选机制，须用慢请求与相关阻塞 span 的同一时间窗口证据定位。公网 `/health` 失败不自动等于 Bridge 退出。

本 P0.5 限定为**最小可观测性 + 证据驱动的窄修复**：

1. 为现有 `stopBridge()` 及实际管理关闭入口增加来源/原因枚举和有界生命周期事件：`shutdown_requested`、`shutdown_begin`、`shutdown_complete`；区分 `SIGINT`/`SIGTERM`。只记录能可靠获得的本机发起者信息。
2. 使用不吞掉默认异常的 `uncaughtExceptionMonitor` 和适度 `exit` 观测，记录可知的退出信息；缺记录只标 UNKNOWN，不推定一定是被强制终止。
3. 若属于“进程活着但卡死”，以默认关闭的最小 Event Loop lag / 请求 span/同步热点 trace 定向关联；观测自身不得再使用每事件同步写盘，不建设长期遥测或监控平台。
4. 若进程继续无声消失，才考虑临时**外部只读死亡探针**；绝不借此自动重启、杀进程或循环恢复。
5. root cause 未证实时只报告候选；取得相关证据后只修有依据的实际问题。

交付：能区分退出/卡死的事件记录、最小证据或明确 `ROOT_CAUSE_PENDING`、定向测试及剩余风险。**不得为等待下一次复现而无限阻塞 Stage 1**：低风险取证准备已通过且当前不持续掉线时，可继续 Stage 1；修改/部署正式 Runtime、计划任务或生产日志配置需另行授权。

### Stage 1 — Full Access / Git Write 一致性与失败归因

**这是 V1.5 的 P0。Stage 0 已 PASS；P0.5 完成最小归因准备后可以直接施工。**

#### 2026-10-25 真实阻断案例（Stage 1 必须覆盖）

- 当前有效授权曾核对为 `baselineMode=level1`、`effectiveMode=level2`、`sessionElevation.active=true`；`execution_run` 可直接完成 Git commit/merge/branch。
- 同一 C2C workspace 的结构化 Git approval 列表实测 `approvals=[]`；结构化 `git_write` 因找不到 repository approval 返回 `NOT_APPROVED`，连 `branch_list` 也遭拒绝。
- 当前 approval 匹配依赖 `workspaceId + repositoryIdentity + canonicalRepositoryPath`，所以相同 Git common repository 的不同 worktree 也可能重复审批。
- 这说明**授权语义冲突已真实发生**，并不说明 Git 仓库损坏、Level2 session grant 失效或 C2C 完全断线。`approvals=[]` 是当次 workspace 快照，不作为未来永久事实。
- Stage 1 优先裁定结构化 `git_write` 在有效 Full Access 下应如何利用已有用户授权，同时保留必要的 expected HEAD / branch / remote / repository identity 防误写验证；Restricted/Level1 边界另行保留。
- 不能把所有 `git_write` 拒绝简单改成自动执行 `execution_run` 绕过；只允许在用户已经授权且满足安全合同的正常操作路径上继续任务。

**验收必须覆盖：无仓库审批但 Level2 有效时的普通 Git 与结构化 Git 对照；`branch_list` 等只读结构化操作是否被错误拦截；新 worktree 的重复审批；拒绝后可恢复操作。**

目标：

让已经授权的正常开发任务尽量直接完成；真正需要拒绝时，AI 能知道为什么，以及下一步该做什么。

主要调查/修改区域：

- `src/mcp/server.ts`
- `src/mcp/v13-tools.ts`
- `src/git-write/registry.ts`
- `src/git-write/planner.ts`
- `src/git-write/security.ts`
- `src/git-write/types.ts`
- 必要的 CLI/Skill/测试文件。

必须先做产品决策：

#### 模式 A：Full Access

Level2 Full Access 已经授权通用本机执行。

正常 Git 操作应尽量与这个授权模型一致。

结构化 `git_write` 可以继续提供额外安全价值，但不能无理由让同一项合法 Git 操作比 `execution_run` 更难完成。

#### 模式 B：Restricted / Level1

结构化 Git Write 可以继续维持独立 repository / operation / branch / remote policy。

不得因为改善 Full Access 体验而降低 Restricted 模式的安全边界。

#### 对外失败分类

V1.5 不要求第一版一次暴露十几种用户级错误码。

首版优先四类：

- `LOCAL_AUTH_REQUIRED`
- `REPOSITORY_POLICY_DENIED`
- `REPOSITORY_IDENTITY_CHANGED`
- `STATE_CHANGED`

内部可以继续保留更细原因，例如：

- branch 不允许；
- remote 不允许；
- remote URL mismatch；
- operation 不允许；
- policy digest stale。

只有当不同技术原因需要不同用户动作时，才提升成新的对外 reason code。

#### 修复体验要求

一次拒绝后的完整体验应是：

1. 告诉 AI 为什么拒绝；
2. 判断是否存在已经授权的合法路径；
3. 如果确实需要本机审批，只给出明确的一次本机动作；
4. 完成后由原 enforcement point 重新验证；
5. 原任务继续，而不是要求用户重新派发整个任务。

#### Worktree approval

可以评估 Git common repository identity 复用 approval，但必须同时证明：

- common-dir / repository identity 一致；
- worktree 确实属于同一 repository；
- branch 仍允许；
- remote 仍允许；
- operation 仍允许。

禁止采用“父目录批准，因此子目录自动批准”的路径继承。

Stage 1 验收重点：

- Full Access 下合法 Git 工作不出现无价值的重复审批；
- Restricted/Level1 不退化；
- 拒绝原因明确且能指导下一步；
- stale HEAD / branch / repository identity 仍 fail closed。

### Stage 2 — 恢复体验 + ChatGPT 路由

目标：

当 C2C 出问题时，优先利用现有恢复能力，让用户容易恢复正常工作，而不是先建设常驻自动恢复系统。Stage 2 继承 P0.5 得到的退出/卡死分类和证据，只处理实际恢复缺口，不重建第二套诊断权威。现有 `doctor` 默认行为包含 auto-repair，`--no-fix` 才是只读诊断；新增/展示的“查看状态”入口必须明确只读，不得误导用户以为默认 `doctor` 不会启动 Bridge/Tunnel。

主要复用：

- `status`
- `restore`
- `doctor`
- Launcher
- `src/process/recovery.ts`
- `src/process/daemon.ts`
- `src/bridge/instance-lock.ts`
- `src/bridge/runtime.ts`

重点场景：

1. Bridge 正常；
2. Bridge 明确停止；
3. Bridge identity 不明确；
4. Named public self-probe degraded 但真实工具调用正常；
5. Tunnel 确实断开；
6. 有活动 Job；
7. Task 处于未知副作用状态；
8. Runtime/Launcher 指向错误版本。

新入口必须明确区分：

- 查看状态：默认只读；
- 恢复：明确动作；
- 自动修复：不得修改授权、重新配对、扩大权限或重放未知副作用操作。

#### Watchdog 处理

旧 watchdog worktree 只作为参考。

本 Stage 可以选择性复用低风险机制，例如：

- Runtime identity 检查；
- 已验证 Bridge owner 检查；
- 活动 Job/Task 判断；
- 终止前的身份确认。

但默认不引入：

- 常驻 5 秒 watchdog；
- 自动杀 Bridge；
- recovery lease 体系；
- 多层自动恢复 policy；
- 独立 active-runtime authority；
- 完整 failure snapshot 系统。

只有真实测试证明现有恢复链无法满足目标时，才针对那个缺口引入最小机制。

#### ChatGPT / Codex 路由

同期更新 Skill / AI Guide：

- Codex 本机：Native Tools 优先；
- ChatGPT 网页端访问本机：C2C 优先；
- C2C 完全离线、GUI/UAC、明确缺能力、用户明确要求时，Remote 才是正常 fallback；
- OAuth、Level2、repository policy、安全拒绝不得通过 Remote 绕过。

V1.5 不要求新增正式“路由统计系统”。

Stage 2 验收重点：

- 典型停止/重启能恢复；
- identity 不明确时不误杀；
- 长任务不被错误重放；
- 恢复后已有 Job/Task 仍可合法查询；
- 连续失败不无限重启；
- 自动恢复做不到时，用户仍有清晰的手动恢复路径；
- AI 不因为旧 Skill 或错误归因无意义地转用 Remote。

### Stage 3 — 组合回归与真实交付验收

不再开发大型新模块。

执行：

- 相关定向测试；
- typecheck/build；
- Windows 实机验证；
- Full Access / Git Write 验收；
- Level1 安全回归；
- Job/Task 恢复语义；
- ChatGPT 在线工具可见性和真实调用；
- Remote parity 非退化检查；
- Skill / Runbook / 用户说明同步。

最终 Release 是否合并、推送、部署，仍是单独发布决策。

## 5. V1.5 最终完成标准

V1.5 不按“新增了多少模块、错误码、状态字段”验收。

只看以下结果：

| 验收目标 | 完成标准 |
| --- | --- |
| 普通开发 | Full Access 下，获授权命令与 Git 工作不出现不必要的额外审批 |
| 权限拒绝 | 能区分权限不足、仓库策略拒绝、repository identity 变化和 state stale，并说明下一步 |
| 长任务 | 已有 Job/Task 可继续查询；不错误重放 |
| 服务恢复 | 典型停止/重启后可恢复；identity 不明确时不误杀 |
| 客户端交付 | 本版本承诺的工具在真实 ChatGPT 对话可见、可调用 |
| 安全回归 | Level1、OAuth、敏感路径、Native execution 和 Git fail-closed 边界不退化 |
| 运维成本 | 不为了 V1.5 要求用户维护额外后台服务、监控系统或大量重复审批 |

这七项全部达到，才认为 V1.5 主目标完成。P0.5 是真实故障驱动的限时取证任务，不要求所有历史掉线都拿到事后唯一根因；但必须避免“无法归因”被写成“已经修复”。

## 6. 最小验收矩阵

### Git / Full Access

- G01：Level2 Full Access 下合法普通 Git 操作可完成；
- G02：结构化 `git_write` 对同一合法目标不存在无解释的额外摩擦；
- G03：Level1/Restricted 下 repository policy 仍然有效；
- G04：branch / remote / repository identity 不匹配时继续拒绝；
- G05：HEAD/state 变化时继续 fail closed；
- G06：拒绝后能给出正确下一步，而不是误报 OAuth/连接故障。
- G07：在 `approvals=[]` 且 effective Level2 有效时，普通 Git 可用与结构化 `git_write` 拒绝能被准确区分和修正；
- G08：`branch_list` 等只读操作不得因写审批缺失而产生不合理阻断（若工具设计确需授权，须给出明确理由和合同）；
- G09：同一 Git common repository 不同 worktree 的审批重复问题有明确产品裁决，并保留 branch/remote/operation 校验；
- G10：不以自动转走 `execution_run` 掩盖结构化工具真实授权失败。

### Recovery

- R01：Bridge 明确停止后可通过正式恢复入口恢复；
- R02：Bridge identity 不明确时不误杀；
- R03：正常长 Job 不因恢复检查被终止；
- R04：未知副作用的 Job/Task 不自动 replay；
- R05：恢复后已有 Job/Task 状态可查询；
- R06：连续失败不会形成无限重启；
- R07：Named self-probe degraded 但真实调用正常时，不误重启健康 Tunnel。
- R08：正常请求关闭时能记录可信的 shutdown reason/source、信号与生命周期；
- R09：PID 已退出但无正常退出证据时保留 `ROOT_CAUSE_PENDING`，不虚构死亡原因；
- R10：进程存活但 `/health` 卡死时，能通过默认关闭的最小 trace 区分 Event Loop 阻塞候选，不因探针造成新同步卡顿；
- R11：采样故障无复现时，可按明确边界收尾 P0.5，不无限等待导致 Stage 1 停工。

### ChatGPT Delivery

- C01：`workspace_info` / `permission_status` 可用；
- C02：本版本承诺的 Batch/Task/Execution 工具真实可见；
- C03：Level2 下最小 `execution_run` 成功；
- C04：Level1 下 Full Access 正确拒绝；
- C05：C2C 安全/授权拒绝不会被 Remote 绕过；
- C06：C2C 真正离线时存在独立恢复路径。

## 7. 施工纪律

- V1.5 必须从 V1.4 Final 的确认基线施工；

- 每个阶段只修改与该阶段目标有关的模块；

  - 设计决策；
  - 实施差异；
  - 测试；

  - 剩余风险；
