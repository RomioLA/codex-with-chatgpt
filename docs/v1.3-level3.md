# C2C Local V1.3 Level 3 执行审批

Level 3 为本机显式开启的单次命令授权，独立于 Level 1/2 的包脚本信任表。默认关闭；Level 1/2 的授权不会提升、继承或转换为 Level 3 授权。

## 请求与授权

远程请求通过 `createLevel3Request(workspace, clientId, spec)` 进入 `pending`。请求必须绑定 workspace、选定的 Git repository、OAuth clientId、超时、精确可执行文件、工作目录、参数或完整 shell command，以及明确列出的材料文件。创建请求不会启动进程，也不会创建执行权限。远程回执只含 requestId、digest 和过期时间；安全预览可以显示已检查过的命令内容，但不返回状态目录、材料哈希或文件 identity。

本机 CLI 使用 `setLevel3Enabled(workspaceId, true, true)` 开启功能，再通过 `listLevel3Requests` 和 `getLevel3Request` 检查完整请求。请求 10 分钟后过期。CLI 审批时必须提供本机选择的 `risk`：

- `development` 用于本机认为属于开发任务的命令。
- `destructive-system` 必须同时明确提供 `allowSystem: true`，对应 CLI 的 `--allow-system`。

风险分类只接受本机审批参数，不能由远程请求自行声明。Level 3 不会提升权限，也不声称把命令限制在 workspace 内；审批人应检查完整命令和作用范围。命令中检测到已知凭据形式、敏感键赋值或私钥内容时会拒绝创建请求，避免把凭据保存进审批状态。

## 执行边界

可执行文件必须是绝对 `.exe` 路径。`powershell` 只接受 `pwsh.exe`，由 native runner 固定附加 `-NoProfile -NonInteractive -Command`；`cmd` 只接受 `cmd.exe`，由 native runner 固定附加 `/D /S /C`。两种 shell 的 `command` 原文完整绑定在审批摘要中，shell `args` 必须为空。`program` 使用直接启动，逐项保留 `args`，不经过 shell。

工作目录与所选 repository 必须位于 workspace 内；显式材料必须是 repository 内非敏感普通文件。申请、审批和排队启动前分别计算并核对 executable、cwd 和材料的 file identity/hash。Level 3 将批准快照写入 protected state 下的 manifest；native runner 在执行期间锁定 manifest 和材料，并再次检查身份与哈希。Job Object、helper/launcher 完整性及子进程树清理仍由既有 native 执行边界负责。

`consumeLevel3Request` 把 `approved` 请求一次性改为 `consumed`，并在创建 queued job 时返回 repository、request 元数据和 GenericCommand。真正启动前，supervisor 必须调用 `resolveConsumedLevel3Request` 再次核对授权材料；该操作单次改为 `launching`。重复消费、重复 launch resolve、clientId 不匹配、digest 不匹配、过期或材料变化都失败关闭。服务重启后的 interrupted job 不得重跑。

## 本机管理

`revokeLevel3Request(workspaceId, requestId, true)` 撤销单个未结束请求。`setLevel3Enabled(workspaceId, false, true)` 撤销所有尚未结束的请求；supervisor 通过 permission poll 停止已启动任务。审批状态、命令和 manifest 存放在 `getStateDir()/execution/level3/<workspaceId>`，该目录通过现有 protected-state 检查。状态事务使用单 workspace 锁；若检测到现存锁一律返回 `LEVEL3_STORE_BUSY`，不会自动清理或抢占锁。只有本机操作员确认没有活动 owner 后，才可手动检查并恢复遗留锁。
