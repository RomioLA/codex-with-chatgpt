# C2C Local V1.3.2｜已确认变更与收口计划

> 状态：工作文档。只记录已经明确决定的方向与已完成实现；尚未决定的候选能力不写成既定需求。
>
> 版本标签：本文暂以 **V1.3.2** 作为本轮收口版本名。当前 `package.json` 的版本字段是否同步调整，留到发布前统一处理。

## 1. V1.3.2 目标

2026-10-17 最终产品裁决后，V1.3.2 不再以“比 Remote 更窄、通过更多本机审批换安全”为最终目标。

V1.3.2 的最高本机权限模式（当前实现名为 effective `level2`）按 **Full Access** 定义：

- 在相同 Windows 用户、登录 session 与 elevation 下，对普通非 GUI 本机开发和主机操作达到 Remote Desktop Commander 的关键能力覆盖；
- 用户本机选择 Full Access，本身就是普通操作的授权边界；
- 普通通用命令执行不得再要求逐命令人工审批、digest 确认、trusted-command 预登记或额外 Level 3 feature switch；
- C2C 可以继续通过 OAuth/client binding、workspace/repository identity、Job Object、输出脱敏、审计、stale protection、reparse/path validation、crash safety 等方式做得比 Remote 更结构化、更可控，但这些安全增强不能用于静默降低 Full Access 能力；
- readonly / Level 1 等 restricted mode 仍然保留更窄权限；
- ChatGPT 仍不能自行把自己从低权限提升为 Full Access。

权威非回退合同：

- 根目录 `AGENTS.md`
- `docs/local-permission-model-requirements.zh-CN.md`
- `docs/remote-parity-acceptance.md`

已确定的默认工具策略：

- Workspace 文件、源码、Git、Host Observation、进程、网络和命令执行，默认优先使用 C2C Local。
- Remote Desktop Commander 只保留给 GUI、UAC/交互桌面、C2C 自救/灾难恢复，以及 C2C 尚未真正实现的能力。
- 如果 Remote 能完成而 Full Access C2C 仅因自身额外审批/allowlist/Level 3 gate 无法完成，应记录为 C2C parity gap，而不是把 Remote fallback 常态化。

## 2. 已确认：Level 1 持久，Level 2 仅当前 Windows 登录会话

### Level 1

Level 1 作为长期基础权限，持久保存并跨 Windows 注销/重启保留。

主要能力：

- Workspace 读取；
- 创建、编辑、替换文件；
- Workspace 内部移动；
- 策略允许的外部文本读取。

Level 1 不自动获得：

- Workspace 删除；
- Git Write；
- trusted execution；
- Level 3 命令审批。

### Level 2

Level 2 改为 **当前 Windows 登录会话临时提升**，不再作为长期持久权限。

目标语义：

- `c2c permission 2 -w <workspace>` 为当前登录会话创建临时 Level 2 grant；
- 同一登录会话中，Bridge / Runtime / Tunnel 重启后仍有效；
- Windows 注销或重启后自动失效；
- 失效后回落到持久 Level 1 baseline；
- 不依赖 shutdown hook / logout cleanup；
- 无法可靠确认当前 Windows session identity 时，fail closed 到 baseline。

当前本地实现已经完成：

`7e1c4e2aea6cfe6d61673e1cc1e7fa83c5ac47f7`
`feat: make level2 session-scoped`

当前实现事实：

- session identity 绑定 boot 标识/时间、用户 SID、session ID 与 token AuthenticationId；
- CLI / MCP 状态返回 baseline、effective mode 和 session elevation；
- MCP 不暴露内部 session identity 指纹；
- 旧持久 `level2` 迁移为 Level 1 baseline + 当前会话 Level 2 grant；
- 缺失或损坏状态继续 fail closed 为 `readonly`。

当前尚未完成：

- Production 部署；
- 真实 Windows logout/login 验收；
- 真实 Windows reboot 验收。

## 3. 已确认：Full Access 通用执行不依赖 Level 3 逐条审批

历史 V1.3 Level 3 的 request → digest → local approval → single-use launch 模型可以保留用于 restricted mode、兼容路径、审计或特殊能力，但 **不再是 Full Access 通用命令执行的最终授权模型**。

V1.3.2 Full Access 必须具备直接通用执行能力，包括：

- PowerShell；
- CMD；
- 直接 executable；
- Node / Python；
- package manager、test、build、lint、typecheck；
- 普通 Git 与开发工具；
- 合法 cwd；
- 长任务 status/output/cancel；
- 与相同 Windows 用户/session/elevation 下 Remote 相当的普通非 GUI 主机操作。

Full Access 下不得把以下任一项作为普通执行的必经条件：

- 每条命令人工确认；
- 每条命令 digest 审批；
- trusted-command registry；
- 单独开启 Level 3 feature switch；
- 仅允许预定义 safe-development 命令图。

Level 3 风险分类器、material binding、TOCTOU recheck 等既有实现可以继续复用于执行安全、审计或 restricted mode，但不得形成 Full Access 的功能天花板。

ChatGPT 仍不能自行改变本机 permission mode；Full Access 必须由用户本机明确选择。

## 4. 已确认：新增结构化只读 `git_compare`

当前 C2C `git_diff` 只支持：

- `unstaged`
- `staged`
- `head`

它不能直接比较两个历史 Commit。

这已经在真实只读审核中造成过：

- Branch / HEAD / status / source / search 都可由 C2C 完成；
- 仅为了 `git diff <base> <head>` 切换到 Remote。

GitHub `compare_commits` 可以提供 changed files 及 additions / deletions 等统计，但当前接口不返回完整 patch，因此不能完全替代本地历史 diff 审查。

V1.3.2 确认增加一个纯只读结构化接口：

`git_compare`

建议参数：

```text
repository_path
base_commit
head_commit
path?        # 可选
offset?      # diff 字节分页
max_bytes?   # diff 字节分页
```

第一版语义明确等价于：

```text
git diff <base_commit> <head_commit> -- [path]
```

不混入 `A...B` merge-base 语义。

建议返回：

```text
baseCommit
headCommit
files[]
  path
  previousPath?
  status
  additions
  deletions
  binary
diff
totalBytes
offset
returnedBytes
hasMore
nextOffset
```

安全边界：

- 只要求 `git.read`；
- 不需要 Git Write approval；
- 不需要 Level 3；
- 不接受任意 Git 参数；
- `repository_path` 必须是 Workspace 内合法 repo/worktree；
- `path` 继续经过 canonical / sensitive-path 检查；
- 禁止 option injection；
- 关闭 external diff / textconv / hooks / 不可信 helper；
- diff 使用 bounded byte pagination；
- rename / binary 行为必须明确。

完成后，类似：

> 审查 Integration 基线到 WORK HEAD 的实际代码变化

应该可以完全通过：

`git_info → git_compare → read_file / search_workspace`

完成，而不需要 Remote 或 Level 3。

## 5. 已确认：特殊二进制/数据库格式优先 C2C Full Access 本机解析，不立即扩展泛用 binary API

真实调查已经遇到 Electron / Chromium LevelDB。

当前 C2C：

- `read_file` / `read_external_file` 面向 UTF-8 文本；
- `path_inspect` 只返回元数据；
- LevelDB 属于二进制数据库；
- 对 LevelDB 直接做字符串扫描，只能证明物理文件中存在过某个值，不能证明当前逻辑键最终有效值。

已确定的工具选择顺序：

1. 先使用 C2C 结构化工具检查日志、源码、配置路径和调用链；
2. 遇到 LevelDB、SQLite、压缩包或其他特殊格式时，不因为没有专用 parser 就立刻切 Remote；
3. 在 Full Access 下优先通过 C2C 通用执行运行合适的本机解析程序/命令；
4. restricted mode 可继续使用 Level 3 / trusted execution 等窄路径；只有 C2C 确实缺少能力或不可用时，再使用 Remote。

本轮 **不确认新增泛用 raw binary read API**。

`leveldb_inspect` 也暂不列为 V1.3.2 必做项；如果后续出现高频真实需求，再单独立项。

## 6. 已确认：C2C 写入失败后才允许 Remote fallback，并调查 `edit_file EPERM`

新的真实使用报告来自 `C:\codex\taptap-sea`：

- C2C 可以正确识别嵌套仓库、`main`、真实 HEAD 和 dirty 状态；
- C2C 可以完整读取总控文档；
- 对项目文件修改时，`edit_file` 在有效 `level2` 状态下返回了 `EPERM`；
- 随后才使用 Remote 做两个很小的精确替换。

由此确认默认工具选择顺序：

1. C2C 读取仓库 / Git / 文件；
2. C2C 完成文件修改；
3. C2C 做状态与结果核对；
4. 只有具体 C2C 操作已经真实失败、C2C 明确不支持，或权限策略明确阻止时，才允许 Remote fallback；
5. fallback 时必须记录 C2C 的实际失败原因，不能只因为 Remote 可以直接写绝对路径就优先切换。

这条规则的目的不是禁止 Remote，而是避免通用远程终端绕过结构化 Workspace、`contentHash` stale protection、Git 结构化结果和更窄的操作边界。

### `edit_file EPERM` 必须调查

`level2` 下读取正常、但单个普通项目文件 `edit_file` 返回 `EPERM`，目前根因尚未确认。

V1.3.2 将其列为必须完成的兼容性/诊断调查：

- 区分 C2C policy denial 与底层 Windows filesystem `EPERM`；
- 检查 readonly attribute、ACL、文件锁、atomic replace/rename、临时文件落点、路径 canonicalization 等实际失败点；
- 若属于 C2C 写入实现问题，修复后补回归测试；
- 若属于宿主文件状态或外部锁，错误结果必须足够结构化，让调用方知道为什么失败以及是否适合 fallback；
- 不得把 `EPERM` 自动解释为“Level 2 不够”，也不得因此自动升级权限或绕过本机控制面。

验收要求：

- 对正常可写 Workspace 文件，Level 1/Level 2 下 `edit_file` 均能按各自权限正常工作；
- stale `contentHash` 仍必须拒绝覆盖；
- policy denial、ACL/readonly、sharing violation/lock、atomic replacement failure 等错误应尽量可区分；
- C2C 写入真实失败后，Remote fallback 仍是允许的备用路径。

## 7. 历史阻塞记录：Git Write policy 与 Level 3 material binding

一次 TapTap Integration 收口任务曾暴露：

- 结构化 Git 创建 Integration branch/worktree 返回 `NOT_APPROVED`；
- 随后尝试旧 Level 3 精确命令申请，返回 `LEVEL3_MATERIAL_CHANGED`；
- Remote 当时离线；
- 任务因此无法继续。

这段记录保留作为“为什么 Remote parity 必须落实”的真实证据，而不再定义 V1.3.2 Full Access 的最终授权方式。

### `NOT_APPROVED`

结构化 `git_write` 可以继续保留 repository policy，作为更安全、可审计的首选接口。

但 Full Access 不能因为 `git_write` 未预审批就完全失去普通 Git 能力。相同 Windows 用户/session/elevation 下，Remote 能执行的正常 Git 开发操作，Full Access 必须存在无需逐命令 C2C 审批的可用执行路径。

换句话说：

- `git_write` 的 policy 可以继续存在；
- Full Access 不等于“自动绕过 Git/OS/remote 自身权限”；
- 但缺少 C2C 自己的 repository approval 不应再成为 Full Access 被迫切 Remote 的根因；
- push、reset、clean、rm、branch delete 等操作是否需要产品级例外，必须明确写入 Remote Parity 合同，不能由旧 Level 3 分类器自动决定。

### `LEVEL3_MATERIAL_CHANGED`

该错误继续有诊断价值：它表示旧 Level 3 material binding 无法稳定验证某个执行目标或材料。

但 Full Access generic execution 不应依赖：

`request → local inspect → approve → single-use launch`

作为唯一执行路径。

因此后续应把 `LEVEL3_MATERIAL_CHANGED` 视为：

- restricted / historical Level 3 路径的错误；
- 或底层 material/TOCTOU 安全机制需要改进的信号；

而不是 Full Access 普通命令“必须停下等待人工审批”的产品规则。

### C2C internal failure

单次 internal failure 先记录为运行时可靠性事件，不据此认定为独立根因。

如果 V1.3.2 实施或验收期间再次出现，应收集：

- 发生前最后一个 C2C tool；
- Bridge/runtime 状态；
- transport/MCP error；
- 是否可通过同一会话下一次调用恢复；
- 是否与 Level 3 / Git Write 操作存在稳定相关性。

### 与 Integration clean gate 无关的事项

B 分支残留的 4 组 untracked evidence 是项目 clean gate / 工作区治理问题，不属于 C2C 权限模型缺陷。处理时应保留证据，不得为了通过 clean gate 机械 commit、clean 或删除。

## 8. 权限边界：restricted mode 保持窄权限，Full Access 以 Remote Parity 为准

### 文件权限

- `readonly`
- persistent Level 1 baseline
- session-only Level 2 elevation / Full Access

readonly 与 Level 1 的现有边界继续有效，不能被 shell 或其他工具旁路。

### Full Access

effective Level 2 是 V1.3.2 当前最高本机权限，产品语义按 Full Access 验收。

Full Access 必须能够完成普通本机开发与主机操作闭环，包括文件、命令、Git、进程及同用户权限下的必要系统操作。

### Git

结构化 `git_write` 可以继续提供更安全、可审计的首选路径，但 Full Access 不能因为 repository policy 未预登记就彻底失去 Remote 已有的普通 Git 操作能力。

Full Access 的普通 Git 操作不得再要求每次人工审批。真实 OS 权限、remote authentication、branch protection 和服务端策略仍然照常生效。

### Bounded execution / trusted registry

trusted-command registry 可以继续服务 restricted mode 和快速安全路径，但不是 Full Access generic execution 的前置条件。

### Level 3

Level 3 历史审批链可以保留兼容性和 restricted-mode 用途，但 Full Access generic execution 不依赖其 feature switch 或逐命令审批。

### Windows Practical Atomic Edit 决议与实现（2026-10-17）

- 用户明确将本机普通文件编辑的威胁模型调整为 **Practical Atomic Edit**。此前 RECOVERY-03 记录的 `ReplaceFileW` Rename/Swap 竞态仍然成立；同权限恶意进程可以在最后路径检查与 publication 之间抢占路径，本实现不声称消除该竞态，也不把 `ReplaceFileW` 描述为 adversarial identity CAS。
- Windows replace/edit 使用同目录随机临时文件、exclusive create、完整写入与 `fsync`，随后由既有受完整性元数据保护的 `c2c-execution-helper.exe --atomic-replace` 单次启动完成 final validation、`ReplaceFileW` 和 post-verification。每个 C2C helper 会按原目标 Volume/File ID 获取本地 named mutex，覆盖 final validation 至 post-verification，确保普通 C2C writer 只有一个能以相同 expected hash 发布；普通外部编辑器变化在 helper 校验时返回 stale 或 fail closed。
- helper 发布前验证 canonical destination/source、同目录、regular file、reparse 状态、readonly、Volume/File ID、SHA-256 与 owner/group/DACL；目标句柄申请目标自身的 `FILE_WRITE_DATA|DELETE` 权限，因此父目录单独授予 `DELETE_CHILD` 不能绕过目标 DACL 的写拒绝。发布后验证新 hash、关键文件属性和 owner/group/DACL。替换失败的诊断会区分 publication 前与 publication 后（`operationApplied`），native `ERROR` 输出字段由 TypeScript 严格校验。
- Win32 打开目标遇到 sharing/lock violation 时在 helper 内最多重试 10 次、每次 10 ms；权限拒绝不重试。通用非 ACL Windows 原子文件状态更新若 Node `renameSync` 遇到 `EPERM/EBUSY`，也最多重试 10 次、每次 10 ms；本机 600 次同目录替换复现出 6 次瞬态拒绝，有界重试后 600 次通过。正常首发成功没有 sleep；replace/edit 性能不增加额外 helper 启动。
- 保留 workspace/external 原有权限和敏感路径策略；replace/edit 源文件最多 10 MiB，提交内容最多 1 MiB UTF-8。前者限制双份文件缓冲与编辑成本，后者沿用 MCP 文本写入入口的请求体上限。其他二进制、device、目录、reparse 和 protected 路径仍由现有路径策略拒绝。
- 崩溃矩阵：部分 temp 写入后退出、temp flush 后 publication 前退出，原目标保持完整旧内容；publication 后退出，目标为完整新内容。随机 temp 名称含目标 basename、PID 与 UUID，可识别为 C2C 暂存文件；不在每次启动扫描目录或自动删除可能仍被使用的临时文件。
- 双进程 Windows 竞争测试使用两个独立 Node/C2C writer、相同 expected hash 和 5 MiB 原文件：一个成功、另一个 `STALE_FILE`，最终字节 hash 等于胜者返回值。Write Safety 全套 37/37 通过，含 stale、普通 editor、rename/delete、readonly、ACL、崩溃、原子可见性与 DACL/属性验证。
