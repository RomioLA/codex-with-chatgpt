# V1.3 F-05 容量轮转证据

本证据由 `tests/v13-capacity-rotation.test.ts` 覆盖，验证任务索引、Level 3 审批历史及 Git 计划在容量轮转时保留完整审计记录，并拒绝不安全的归档输入。

## 验收项

- **Execution JobStore：** 连续创建并终态替换 300 条任务，在中途重建 Store；轮转后活跃索引保持 50 条，最早任务仍可按任务 ID 与幂等键读取，已写入的输出仍可读。
- **Level 3：** 在 256 条历史记录上触发轮转，确认新请求可创建；安全撤销记录可从档案读取，未结束的 `consumed` / `launching` 记录和未确认清理的终态结果留在活动状态文件中，且未被归档。
- **Git 计划：** 安全终态 Job 的计划材料从活动计划路径移入档案；旧计划仍可读取，但执行解析拒绝归档计划。未知文件、重解析点目录项和摘要不匹配均被拒绝。

## Fixture 来源与边界

JobStore 覆盖使用 300 条 Store API 创建和终态替换记录，不启动任务进程。Level 3 容量测试由 1 条真实 API 创建并撤销的记录作为模板，再明确种入 251 条安全终态状态记录；另外 4 条 `consumed`、`launching` 和未确认结果记录通过审批 API 生命周期生成。种子不代表 251 次真实 API 请求或 Native 任务。测试使用一个 Git 仓库和一个小型 `FakeProgram` 文件；程序仅供审批快照引用，**不会执行 Native 程序**。

Git 计划测试只进行计划读取、档案移动和拒绝路径检查。测试夹具由 `makeTmpDir` 创建并保留，不自动删除目录或文件。

## 容量语义

JobStore 的 50 条和 Level 3 的 256 条是活动索引/状态记录容量。安全终态被写成完整身份档案；JobStore 输出文件也继续保留。容量数字本身不代表磁盘无限保留策略。此证据范围没有定义档案总量上限或档案清理保留策略。

## 执行状态

已串行运行，4/4 通过，日志 `.tooling-security-strengthened-final.log`。JobStore 的 300 次状态循环不是 300 次真实 Native 执行。读取不存在的档案不创建新目录；写入才创建并核验档案路径。最终全量回归见 `v1.3-security-fix-report.md`。

Windows 高频原子替换实验观察到暂时 EPERM；只对 Windows EPERM/EBUSY/EACCES 最多重试 10×10ms，仍使用 rename 原子替换，不 unlink 目标，不把撤销 BUSY 变成成功。异常、未知目录、校验冲突与占满的活动/不确定记录继续失败关闭；不按时间猜测清理所有权。
