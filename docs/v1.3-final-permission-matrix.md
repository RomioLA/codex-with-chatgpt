## 正式 reOAuth 与人机步骤

不能靠 refresh 获得新 scope：源码的 refresh rotation 只把旧 refresh token 中已保存的 scope 集复制到新 token，并撤销旧 refresh token。重新获得 scope 必须由 ChatGPT connector 发起新的 OAuth authorization 请求，不能只等待/刷新当前 token。

1. 人类在 ChatGPT 连接器中发起该 workspace 的正常重新授权/重连。客户端应在 OAuth authorize 请求中明确请求所需 scope；请求必须使用 PKCE S256。注意：当前源码在 scope 参数缺失或为空时回退到 `DEFAULT_SCOPES`，其中包括 `system.read`、workspace 写/删、外部写入以及 execution start/cancel 等 scope。为避免无意扩大授权，应发送明确的最小 scope 集并在授权页逐项核对，而不是省略 scope 参数。
2. C2C 本机操作者按正式 pairing 流程生成有效的一次性 pairing code；人类在授权页面核对 workspace 名称和逐项 scope，然后输入该 code 并提交。code 由这台计算机上的 Codex 生成，数分钟后失效。不要分享或记录 code。
3. 要完成授权的 system.read 链，授权请求必须包含 `system.read`，授权页须明确显示 “Read limited host system diagnostics”，操作者本人确认并批准。`system.read` 不授予文件写权限，也不打开 Level 3 或 Git write。
4. 若需要相应能力，scope 请求还须分别显式包含 `git.write`、`execution.run`、`execution.cancel`；要查看 execution job 还需 `execution.jobs.read`。`execution.level3` 是单独可选 scope；当前某些持久化 grant 已有它，但不会因此打开本机 Level 3。scope 请求与 consent 不应包含任何隐藏或万能 scope。
5. ChatGPT 完成 OAuth code exchange 后，客户端保存新 token。之后可以由客户端正常 refresh；refresh 只继承本次明确授权的集合。旧 scope grant不会被新 token 自动合并；不要用旧 client token 的并集推断实际 access token 权限。
6. 人类在本机 CLI 另行审批需要的权限：为 bounded execution 逐项批准可信 recipe；为 `git.write` 精确审批 repository、操作、branch 和 HTTPS remote；只有明确要 Level 3 时才本机启用它，并逐条 inspect/approve request digest。MCP 不能自行更改这些本机控制面状态。

初始审查仅核对静态源码和 Production 元信息；后续正式重连结果见上方更新。本轮未打开本机 Git write、trusted recipe 或 Level 3，也未把缺 scope 的线上操作记成通过。
