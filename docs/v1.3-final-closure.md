## 当前结论

`V1.3 BLOCKED`

唯一剩余 P0 门禁是**真实 ChatGPT Connector 的正式 OAuth scopes 未完整授权，不能完成受控执行与主机观察的线上验收**。
用户已完成一次旧 `C2C local` 重连；回读新 token 仍是旧文件 scope 集。随后用户明确拒绝第二次追加授权。
本轮因此停止触发进一步授权，不扩展既有 token，不绕过 scope，不把本机测试写成线上通过。
Production Cutover 和 Windows 重启验收依赖该门禁，未执行；原 Production Runtime、Task、State 和 rollback 保留。

## 修复内容

1. `src/bridge/runtime.ts` 仅针对 Windows `EPERM` 修正进程存在性；健康与管理员身份仍分别核验。
2. MCP HTTP 的 server/transport 构造、connect 和 request 处理纳入统一错误边界；失败提供随机关联 ID、工具名与失败阶段。日志不记录 token、请求体、文件内容、异常原文或路径；异常元信息使用固定白名单，栈仅保留有限行列数字。
3. Host Observation 复用正式 OAuth 工具元数据与 insufficient-scope challenge，声明独立 `system.read`，不自动扩展 token 或本机权限。

完整工具 → scope → token scope → 本机门禁见 [权限矩阵](v1.3-final-permission-matrix.md)。

## 后续门禁和回退

用户若以后选择继续授权，应先修正实际 Connector 的显式 scope 请求并核对 consent；需要的正式 scope 包含
`workspace.read workspace.search git.read execution.jobs.read execution.run execution.cancel git.write execution.level3 system.read`，
文件写入及外部文件能力再按已选择的用途保留各自 scope。不能靠 refresh 合并不同旧 grant。
本轮用户拒绝后不再自动弹授权，不修改 Connector 配置。

线上授权和本机独立审批就绪后，才恢复剩余 MCP 回归；全部门禁通过后按已有 protected Runtime staging、
Task action-only 更新、正式 restore、Connector 复验、Windows 重启登录的顺序发布。
旧 Runtime `9db60bb4e81554e80cac38136031203f30e396ff` 和对应 Task rollback 证据不得删除。
当前生产进程仍使用旧 Runtime：收口源码需正式部署后才影响该进程和下次登录启动。
